## What actually wins

This is a **judged** contest. An AI judge reads only the **dossier** — 3 screenshots, then ≤64 KB of dashboard source — and picks pairwise winners against 5 written criteria, in order: (1) working radar with full watchlist coverage and screenshots↔code agreement, (2) a value model derived from the snapshot's own figures (never hardcoded names), (3) farm plans with **costs and durations**, (4) a sortable/filterable page with a per-protocol detail view, (5) a designed look, not a pasted framework. So the build optimizes, in that order: **correctness of the board → credibility of the model → concreteness of the farm plans → dashboard usability → visual design**, all inside hard caps (dashboard source <64 KB total, screenshots 300–350 KB each, dossier ≤1.5 MiB).

Feedback loop: every valid dev submission is judged immediately against the house dashboards and returns a provisional win rate + judge reasons. Budget the 10 submissions: ~1 early probe, 3–5 iterations, ≥2 held in reserve, final entry in by **Dec 12**.

## The value model (criterion 2 — the core of the entry)

Peer-multiple valuation, every input from the snapshot, one function for every row, constants stated in `lib/config.ts` and explained on the dashboard's detail view:

1. **Peer multiple per category:** for each category, the winsorized median `mcap_usd / tvl_usd` of its *live-token* protocols (416 available). Sparse categories (<4 peers) fall back to the chain-blended then global median. This grounds implied value in what the market actually pays per TVL dollar for the same kind of protocol.
2. **Base value** = `tvl_usd × category multiple`.
3. **Growth adjustment** from `change_7d` (clamped, damped — a one-week move is a signal, not a destiny).
4. **Maturity adjustment** from age (`listed_at` → days tracked with no token): long-lived, high-TVL, still tokenless ⇒ the launch is a bigger, more credible event; brand-new listings discounted.
5. **Breadth adjustment** from chain count (multi-chain distribution at launch).
6. Deterministic integer rounding; rank by implied value desc, slug asc. Sanity caps so no implied value exceeds a defensible bound (e.g. a small multiple of the largest live peer's mcap in its category).
7. **Board composition:** all **40 watchlist** protocols + the highest-implied-value pre-token protocols below the floor (the radar's "early" finds — ranked by the model, not raw TVL, which is exactly the improvement over the starter). Early finds are held to the **same exclusions as the house's watchlist rule** — no Bridge/Canonical Bridge/Liquid Staking/Liquid Restaking/Restaked BTC/CEX categories, no wrapped/staked/staking name words, no exchange-name prefixes, no versioned pools — otherwise the top of the board fills with bridge and staking wrappers that are not launch candidates at all (the scaffold's first run proved this: Base Bridge and Binance staked ETH topped the unfiltered board). With the strict filter the eligible pool on this snapshot is ~198 rows — comfortably over the 100-row floor. Live-token protocols are *not* board rows; they ship in `data.js` as the comparison set the detail view uses ("trades at $X on $Y TVL — a P/TVL of Z×").
   - *Known v0 wart to fix in the build:* the peer-max cap makes the largest protocols in thin categories tie at exactly the cap value (three Risk Curators at the identical figure in the scaffold run). Soften the cap so the top of the board stays differentiated (e.g. a cap that still grows slowly with TVL past the peer max).
8. **Explainability:** each row carries its components (multiple used, base, growth/maturity/breadth factors) so the detail view can show *why* — the judge rewards a stated model, and the screenshots can show the breakdown.

## Farm plans (criterion 3)

Generated per protocol from **category playbooks** in `lib/farm.ts` (DEX, Lending, Perp DEX, Bridge-adjacent, Yield/Vault, Liquid-Staking-adjacent, Other), parameterized by the protocol's chains and TVL tier. Every plan: **4–6 steps**, each a single concrete action with **capital required, expected time commitment, and cadence** (e.g. "Provide $500–$2,000 of ETH/USDC liquidity on Ethereum; ~30 min to set up, check weekly"), plus an airdrop-realism note where the category warrants it. All steps inside the gate's 20–600 chars. No slogans, no invented protocol-specific facts (steps derive from category + chains + tier only — the snapshot carries nothing else, and inventing features would break screenshots↔code↔data agreement).

## Dashboard (criteria 4–5)

- Vanilla HTML/CSS/JS, **total source < 60 KB** (hard budget; the judge reads it whole or not at all). No framework, no external assets, renders from `window.RADAR` with zero network.
- **Board view:** sortable columns (rank, implied value, TVL, 7d change, age, multiple), filters (watchlist-only toggle, category, chain, min-TVL slider, search), watchlist rows badged, early finds visually distinct.
- **Detail view** per protocol: implied-value breakdown (the model, in numbers), live peer comparisons, full farm plan as a checklist with costs/time, snapshot facts.
- **Design:** a deliberate dark "radar" identity — one accent color, mono display figures, consistent spacing scale, dense but legible table. Built to screenshot well at 1440×1000.
- **Screenshots:** render the *actual built page* (headless browser — see Risks) at 1440×1000: board, one top protocol's detail, one filtered view; compress each to 300–350 KB PNG.
